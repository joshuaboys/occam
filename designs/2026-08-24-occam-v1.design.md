## Problem

Calling `claude -p`, `codex exec`, or `grok -p` directly does not give a stable contract. Each CLI has different flags, stdin behaviour, JSON shapes, timeouts, and exit codes. A shell script that works on one developer's machine fails on another's, even when both have a coding agent installed.

The previous Occam spec tried to solve this by becoming a small agent framework: provider SDKs, API keys, an Occam-owned tool loop, skills, and a Bun binary. That is the wrong product. The coding-agent CLIs already own intelligence, tools, MCP, and auth. Occam should not compete with them.

## Design

Occam is a **stateless Unix-style execution layer for bounded, single-shot agent work**, using coding-agent CLIs the user already has installed and authenticated.

```text
               OCCAM

stdin ────────────────┐
args ─────────────────┤
task definition ──────┤
                      ▼
                 bounded run
                      │
                local driver
             ┌────────┼────────┐
           codex    claude    grok
             └────────┼────────┘
                      │
                      ▼
              normalised result
                      │
             stdout / JSON / exit
```

Occam is not the intelligence. Occam is the execution contract around locally available intelligence.

The important abstraction is not “provider”. It is a **driver** over an existing local agent CLI.

---

### 1. Product thesis

Occam exists to make this safe and portable:

```bash
git diff main...HEAD | occam review
```

A script using Occam must not need to know whether the executor is Codex, Claude Code, or Grok. The user's existing CLI login is authoritative. Occam invokes that CLI non-interactively, bounds the run, and normalises the result.

Occam MUST remain: stateless, single-shot, local, shell-native, non-interactive by default, bounded, disposable, easy to script, independent of any particular coding-agent CLI.

Occam MUST NOT become: a persistent agent, daemon, conversational agent, session manager, orchestration engine, multi-agent framework, memory system, workflow engine, hosted runtime, provider SDK, authentication broker, MCP platform, or a second tool-use runtime competing with Codex/Claude/Grok.

### 2. Why Occam versus `claude -p` / `codex exec`

The product test, applied to every v1 feature:

> Why would someone use Occam instead of calling `claude -p` or `codex exec` directly?

If a feature does not contribute materially to the answer, it is out of v1.

Occam is worthwhile only because it provides a **stable execution contract** above individual coding-agent CLIs:

| Contract | Direct CLI | Occam |
|----------|------------|-------|
| Named reusable task | copy-paste a prompt | `occam review` |
| Stdin | vendor-specific, easy to inherit a TTY | pipe is context; child stdin is controlled |
| stdout / stderr | mixed diagnostics common | stdout = result, stderr = diagnostics |
| Bounds | vendor-specific, often unbounded | timeout / max-turns / max-output, process killed |
| Driver portability | rewrite the invocation | `--driver`, `OCCAM_DRIVER`, config, fallback |
| Result shape | each CLI emits something different | normalised text or schema-validated JSON |
| Exit codes | vendor-specific | stable Occam codes |
| Auth | each CLI's own login | Occam never owns credentials |

An alias around one CLI is not Occam. A thin flag translator is not Occam. If the only value is “slightly different CLI flags”, Occam should not exist.

### 3. Goals and non-goals

**Goals (v1)**

- Named, file-defined tasks with instructions, output mode, and limits.
- Predictable stdin, cwd, and process lifecycle.
- Driver-independent invocation and result semantics.
- Clean stdout/stderr split suitable for `result="$(… | occam review)"`.
- Optional schema-validated structured output, never silently invalid.
- Stable exit codes independent of the underlying CLI.
- Codex, Claude Code, and Grok as initial drivers. Codex is default.
- Single native binary. No runtime, no daemon.

**Non-goals (v1)**

- Provider authentication, API keys, OAuth, token refresh, direct model APIs.
- Occam-native tools, MCP hosting, or an agent tool loop.
- Skills as a separate runtime concept.
- Sessions, memory, conversation, retries across runs.
- Workflows, DAGs, branching, agents calling agents.
- Model routing as a product. Fallback is environment portability only.
- Isolated VMs / SlicerVM.
- Package registries, remote task stores, hosted execution.

### 4. Architecture

Six modules. No provider SDK. No tool loop.

| Module | Owns |
|--------|------|
| **CLI** | argv, help, `occam <task>`, `--driver`, signals, exit |
| **CFG** | config files, env, driver command paths, fallback list |
| **TSK** | named task TOML: instructions, output, limits, requirements |
| **DRV** | local executable adapters; detect; capability ads; argv mapping |
| **RUN** | one child-process lifecycle, stdin, cwd, timeout, kill, limits |
| **OUT** | stdout/stderr split, JSON/schema validate, one repair, exit codes |

Run assembly is not a module. A run is:

```text
task.instructions + optional --prompt + stdin  →  driver argv/stdin
```

The driver owns reasoning and agent-native tools. Occam owns the process boundary.

### 5. Driver abstraction

A driver is a locally installed executable agent, not a model vendor.

Shared contract stays small. Drivers advertise capabilities; Occam does not pretend to enforce a capability the driver does not expose.

```text
Driver
  id() -> "codex" | "claude" | "grok" | …
  detect() -> missing | unauthenticated | ready
  capabilities() -> structured_output, schema_output, streaming_output,
                    max_turns, tool_allowlist, sandbox_control, ephemeral_mode
  run(RunRequest) -> RunResult
```

**Capability classes**

| Kind | Occam behaviour |
|------|-----------------|
| External | Occam enforces itself (process timeout, max output bytes, kill) |
| Translated | Occam maps onto a driver flag when advertised (`max_turns`, schema, sandbox) |
| Unsupported | requested but not advertised → exit `8` |

Do not force all driver-specific behaviour into a lowest-common-denominator interface. Codex sandbox flags stay in the Codex adapter. Claude `--json-schema` stays in the Claude adapter.

**Initial drivers**

| id | Default command | Non-interactive entry (adapter may probe `--help`) | Notes |
|----|-----------------|-----------------------------------------------------|-------|
| `codex` | `codex` | `codex exec` | **Default driver.** Auth is Codex CLI login. |
| `claude` | `claude` | `claude -p` / `--print` | Native `--output-format`, `--json-schema`, `--max-turns`. |
| `grok` | `grok` | `grok -p` / `--prompt` / `exec` as installed | Probe the local binary; do not freeze a vendor flag set in this spec. |

Driver command is configurable (`command = "codex"`). A user may point `command` at a wrapper (for example [harness-router](https://github.com/joshuaboys/harness-router) `hr`) without Occam knowing about accounts. Occam does not integrate with account routers in v1.

**Selection**

```text
explicit --driver
    ↓
task-level driver
    ↓
OCCAM_DRIVER
    ↓
global config default_driver
    ↓
codex
```

Optional conservative fallback:

```toml
fallback = ["codex", "claude"]
```

(`fallback` rather than `drivers = […]`: TOML cannot attach both an array and a `[drivers.codex]` table to the same key.)

Fallback fires only when the chosen driver is **unavailable** at detect time (missing binary, or clearly unusable). It does not fire on mid-run failure, quality, cost, or model identity. This is so a team script runs with Codex on one machine and Claude on another. It is not a model router.

### 6. Task-definition format

A named task is reusable run semantics. It is not a persona, not a workflow, not an agent.

```toml
[task.review]
instructions = """
Review the supplied change.
Report only material correctness, security, or maintainability issues.
"""
output = "json"
timeout = "90s"
max_turns = 5
```

A task MAY define:

- `instructions`
- preferred `driver`
- input expectations (`stdin = "required" | "optional" | "forbidden"`)
- `output` (`text` | `json`)
- `schema` (path or inline JSON Schema)
- cwd behaviour (`cwd = "invoke"` default, or an explicit path)
- execution limits (`timeout`, `max_turns`, `max_output`)
- `requires` — driver-neutral capability names from the advertised set

A task MUST NOT define: orchestration, branching, DAGs, retries across sessions, other tasks, memory, tools, MCP, or provider/model IDs.

Discovery, in order, later files override earlier task names:

1. `~/.config/occam/tasks.toml` (and `~/.config/occam/config.toml` `[task.*]`)
2. `./occam.toml`
3. `./.occam.toml`

No package registry. No remote tasks. Built-in tasks ship only if they are tiny and obviously useful (`review` may ship as an example, not as product lock-in).

### 7. stdin / stdout / stderr

Shell composability is a hard requirement.

**stdin**

- If stdin is a pipe (or a redirected file), Occam reads it as run input.
- If stdin is a TTY, stdin is empty unless `--prompt` supplies text.
- The child process does **not** inherit the user's stdin.
- Input is passed to the driver as the adapter decides (argv prompt, constructed stdin, or a temp file the adapter owns and deletes). The Occam contract is: the bytes Occam read are the task input.

**stdout / stderr**

| Stream | Contents |
|--------|----------|
| stdout | task result only |
| stderr | diagnostics, progress, driver noise, Occam errors |

This must make the following safe:

```bash
result="$(git diff | occam review)"
```

Diagnostic noise MUST NOT corrupt machine-consumable stdout.

`--quiet` / `-q` suppresses progress on stderr. Errors still go to stderr.

### 8. Structured-output contract

This is one of the strongest reasons Occam exists.

When the user asks for JSON, stdout is the **result body** — the object the next tool consumes. When a schema is declared, that body MUST conform to it.

```bash
cat meeting.txt | occam extract-actions > actions.json   # schema body
git diff | occam review --envelope                       # Occam envelope
```

**Result body** (`output = "json"` or `--json`): the validated JSON value. If a schema is set, this value must satisfy it.

**Envelope** (`--envelope`): Occam metadata wrapping the result.

```json
{
  "version": 1,
  "status": "completed",
  "driver": "codex",
  "task": "review",
  "result": {},
  "duration_ms": 4382
}
```

`status` is one of: `completed`, `driver_failed`, `timeout`, `validation_failed`, `unsupported`.

Driver-native exit codes and a short driver error, when useful, may appear in the envelope (`driver_exit`, `error`) and always on stderr.

**How schema is obtained per driver**

1. If the driver advertises `schema_output` and the task has a schema → pass the schema through native flags (Claude `--json-schema` today).
2. Else if the driver advertises `structured_output` → request JSON and validate after execution.
3. Else if JSON/schema was requested → exit `8` (unsupported), unless the task allows a text-then-extract path. v1 does **not** regex-scrape prose by default.
4. Validate the result body against the schema.
5. If invalid: **one** bounded repair run, feeding the driver the previous output and the validator errors.
6. If still invalid: exit `7`. Do not emit invalid structured output.

Text mode (`output = "text"`, the default): stdout is the driver result text, stripped of adapter framing. No schema.

### 9. Execution limits and lifecycle

A run is **one child-process lifecycle**. No run state survives unless emitted to the caller.

```text
RunRequest
  task, prompt?, stdin?, cwd, output_mode, limits, driver

RunLimits
  timeout?, max_turns?, max_output_bytes?
```

| Limit | Enforcement |
|-------|-------------|
| `timeout` | **External.** Occam kills the process group. Always available. |
| `max_output_bytes` | **External.** Occam stops reading / kills if exceeded. |
| `max_turns` | **Translated** when advertised; else exit `8` if the task requires it. |

Lifecycle:

1. Resolve task, config, driver (and optional unavailable-fallback).
2. `detect()` — missing → exit `3`; unauthenticated → exit `4` with the CLI's own login hint.
3. Refuse unsupported required capabilities → exit `8`.
4. Launch the selected CLI in `cwd`. Controlled stdin. New process group.
5. Collect or stream driver output (stream to stderr if progress; stdout only for the final result, except when the user asked for streaming result text).
6. Enforce timeout and max-output externally.
7. On cancel or timeout: terminate the process group cleanly (SIGTERM, then SIGKILL).
8. Map outcome to Occam exit codes. Exit.

Default timeout if unset: a conservative global default (config, else 120s) so a stuck agent cannot hang a pipeline forever. Tasks may raise it.

v1 streaming: progress on stderr is allowed. Streaming the result to stdout is allowed only in text mode, where there is no schema to validate. JSON/schema waits for the complete body.

### 10. Exit-code contract

Stable, driver-independent:

| Code | Meaning |
|------|---------|
| `0` | completed successfully |
| `2` | invalid invocation or configuration |
| `3` | driver unavailable (not on `PATH`, not executable) |
| `4` | driver authentication or setup required |
| `5` | driver execution failed |
| `6` | timeout |
| `7` | structured output validation failed |
| `8` | unsupported requested capability |

Usage errors from clap (`--help` is 0; bad flags follow clap's convention, normalised to `2` where Occam controls it).

Driver-native exit codes are retained in stderr and in envelope metadata. They never leak as Occam's process exit except via the mapping above.

### 11. Authentication philosophy

Occam MUST NOT own credentials for supported coding-agent CLIs.

The driver:

1. detects whether its executable exists;
2. determines whether execution appears usable/authenticated where feasible (without inventing a login flow);
3. invokes it;
4. surfaces a clear driver-specific error if authentication is required.

Occam tells the user to authenticate with the underlying CLI (`codex login`, `claude /login`, `grok` login — whatever that CLI documents). No Occam `login` command in v1.

### 12. Configuration

Minimal. No hierarchy theatre.

Search (later overrides earlier):

1. `~/.config/occam/config.toml`
2. `./occam.toml`
3. `./.occam.toml`

```toml
default_driver = "codex"
# fallback = ["codex", "claude"]   # optional unavailable-fallback

timeout = "120s"

[drivers.codex]
command = "codex"

[drivers.claude]
command = "claude"

[drivers.grok]
command = "grok"
```

Env: `OCCAM_DRIVER`, plus standard `NO_COLOR`. No Occam API keys.

Task tables may live in the same files (`[task.review]`) or in `~/.config/occam/tasks.toml`.

### 13. Implementation language

**Rust.** This supersedes decision D-001 (Bun/TypeScript).

The revised product is a process-spawning Unix utility: CLI parse, TOML, PATH discovery, pipes, timeouts, JSON Schema, a single static-ish binary. That is a Rust problem, not a TypeScript problem. Bun's startup story does not justify keeping a JS runtime in the product now that Occam no longer embeds provider SDKs.

Suggested crates (not mandatory): `clap`, `tokio`, `serde`, `serde_json`, `toml`, `thiserror`, `tracing`, a JSON Schema crate if schema validation needs one.

Distribution: `cargo install` and a GitHub-release binary. No Node, no Bun.

### 14. Module decomposition

See the Modules table in §4 and `plans/index.aps.md`.

Dropped from the 2026-03-15 spec:

| Old | Fate |
|-----|------|
| PROVIDER | Replaced by DRIVER. No SDKs, no API keys. |
| AGENT | Replaced by TASK. No personas. |
| SKILL | Removed. Instructions live on the task. |
| TOOL | Removed. Drivers own tools. |
| CTX | Not a module. RUN + DRIVER assemble the invocation. |
| RUNTIME / SlicerVM | Removed from v1. Isolation is “one child process, killed on timeout”. |

### 15. v1 scope

- Rust CLI: `occam <task>`, `occam drivers`, `occam tasks`, `--help`, `--version`.
- Drivers: `codex` (default), `claude`, `grok`.
- Task TOML as specified.
- stdin/stdout/stderr contract, `--quiet`, `--json`, `--envelope`, `--schema`, `--driver`, `--cwd`, `--timeout`, `--prompt`.
- External timeout and max-output; translated max-turns when advertised.
- Schema validation + one repair.
- Exit codes 0, 2–8.
- Config files as specified.
- Conservative unavailable-fallback list.

CLI flags stay small. Anything that does not serve the product test is refused.

### 16. Deferred

- Additional drivers (Copilot, OpenCode, Gemini/agy, …).
- Streaming schema output.
- Built-in task library / registry.
- First-class harness-router integration.
- `occam login` (never, unless a future driver has no CLI login of its own).
- Occam-native tools, MCP, skills, memory, sessions, workflows.
- Isolated VMs, sandboxes beyond what the driver already exposes.
- Model routing, load balancing, spend caps.
- Daemon / server mode.
- Windows as a v1 certification target (should compile; Unix is the contract).

### 17. Migration from the current spec

This design **replaces** the 2026-03-15 APS plan. It is not an increment.

- D-001 Bun/TypeScript → **void**. Language is Rust ([ADR 001](../plans/decisions/001-rust.md)).
- D-002 TOML remains, but for **tasks and config**, not “agent definitions”.
- D-003 “no agents SDK as core” is kept and strengthened: no provider SDKs at all.
- D-004 stateless remains.
- Open questions Q-001 (which LLM providers?) and Q-002 (which tools ship?) are **withdrawn**. Occam has drivers, not providers, and ships no tools.
- PR [#2](https://github.com/joshuaboys/occam/pull/2) (Bun AGENT module) is abandoned. Do not merge it.

### 18. Shell examples

```bash
# 1. Review a branch diff. Result is safe to capture.
result="$(git diff main...HEAD | occam review)"

# 2. Same task, different local CLI, same script.
git diff | occam review --driver claude
OCCAM_DRIVER=claude git diff | occam review

# 3. Schema-guaranteed JSON for the next tool in the pipe.
cat incident.json | occam diagnose --json > diagnosis.json

# 4. Kubernetes noise in, structured actions out.
kubectl get events -o json | occam diagnose-k8s

# 5. Meeting notes to an actions file the caller owns.
cat meeting.txt | occam extract-actions > actions.json

# 6. Bound a runaway agent. Occam kills the process, exit 6.
git diff | occam review --timeout 90s

# 7. Inspect what this machine can actually run.
occam drivers
```

Examples 1–5 are why Occam is not an alias. The script never names Codex, Claude, or Grok except when the operator chooses to.

### 19. Acceptance criteria

v1 is Occam, not a thin alias, when all of the following hold:

1. A task file written on a Codex machine runs unchanged on a Claude machine via `--driver`, `OCCAM_DRIVER`, or fallback.
2. `result="$(printf 'x' | occam review)"` does not contain driver progress, logs, or spinner text.
3. Piped stdin never reaches the child as an inherited TTY; a missing required stdin fails with exit `2`.
4. `--timeout 1s` on a long task yields exit `6` and no orphan child.
5. A task with a schema either prints valid JSON on stdout or exits `7` (or `8` if the driver cannot do structured output). It never prints invalid JSON with exit `0`.
6. Unauthenticated Codex yields exit `4` and a message that points at Codex's own login, not an Occam login.
7. `occam drivers` reports missing vs ready without invoking a model.
8. There is no Occam API key, no Occam OAuth, and no Occam tool loop in the binary.

### Hard acceptance test

> If Occam disappeared, what would users have to repeatedly implement themselves around Codex, Claude, and Grok?

They would have to reimplement, in every script and on every machine:

- portable reusable task definitions (instructions, output mode, schema, limits);
- stable stdin semantics (read the pipe, do not leak a TTY into the agent);
- a stdout/stderr split that makes command substitution safe;
- bounded single-run execution with process-group timeout and teardown;
- cross-driver invocation so the script does not hard-code one CLI;
- cross-driver result normalisation;
- schema-guaranteed output with a single repair and a hard fail;
- consistent errors and exit codes, including “not installed” vs “not logged in” vs “timed out”.

That is the product. If a future change leaves only “they would have to type slightly different CLI flags”, delete Occam.
